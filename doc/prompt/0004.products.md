## Prompt — Products collection (MongoDB + Next.js + Zod + seeding)

1. **Create a MongoDB collection named `products`** and define the document structure to support:

   * Product identity (model code, slug)
   * Category/subcategory relationship (by `categoryCode` and `subcategoryCode`, plus optional resolved IDs)
   * Market availability (“specifications provided only for …”) per region/country
   * Marketing highlights (“About product” bullet points)
   * Core specifications (voltage/frequency, power, rpm, duct size, speed control, noise)
   * Working point ranges (air volume min/max and static pressure min/max, with default units)
   * PQ curve series (speed label + curve points)
   * Related products list (model codes)
   * Basic asset placeholders (image/document references), even if not fully implemented yet

2. **Use data from `products` for rendering:**

   * Product list cards (model, subtype label, working-point headline values)
   * Product detail page sections: About product, Specification, PQ Curve, Help Documents, Accessories, Related Products

3. **Seed / bootstrap behavior**

   * On the first successful DB connection (server-side only), check whether the `products` collection exists and contains documents.
   * If the collection is missing OR empty, seed it using the provided initial dataset in the array `SEED_PRODUCTS` in the file `lib\db\seed.ts`.
   * Seeding must be **idempotent**:

     * Use `modelCode` as a unique natural key.
     * Use `bulkWrite` with `updateOne` + `upsert: true`.
     * Create a unique index on `{ modelCode: 1 }`.

4. **Environment variables**

   * Read MongoDB connection parameters from `.env.local`.
   * Use `dotenv-flow` to load environment variables (ensure `.env.local` is part of the loading order).
   * Document required keys in `README.md` (do not commit secrets).

5. **Zod validators + inferred TypeScript types**

   * Create Zod schemas for:

     * `Product` document
     * `ProductMarketSpec` subdocument (region/country applicability + specs)
     * `ProductPQSeries` (speed + points)
     * Optional DTO schemas if you add APIs later (create/update)
   * Infer TypeScript types using `z.infer<typeof Schema>`.
   * Validate at boundaries:

     * When reading from MongoDB (parse documents with Zod)
     * When accepting payload input (if applicable)

6. **Referential consistency**

   * `categoryCode` and `subcategoryCode` must match codes stored in your existing `categories` / `subcategories` collections.
   * Market applicability should reference existing `regions` and `countries`. For seeding convenience:

     * Store `regionCode` and `countryName` (or `countryIso2`) inside `marketSpecs`.
     * Optionally also store `regionId` and `countryId` after resolving them during seeding.

## Recommended `products` document shape (implement this)

Use a structure like:

```ts
// Product document (MongoDB)
{
  _id: ObjectId,

  // identity
  modelCode: string,      // unique, e.g. "15AAQ1"
  slug: string,           // URL-friendly, e.g. "15aaq1"

  // classification
  categoryCode: string,   // e.g. "WALL_MOUNT"
  subcategoryCode: string,// e.g. "AUTOMATIC_SHUTTER"
  // optional denormalized names for UI (or resolve from categories collections)
  categoryName?: string,
  subcategoryName?: string,

  // marketing
  highlights: string[],   // bullet list

  // “Specifications provided only for …” (market-specific)
  marketSpecs: [
    {
      regionCode: string,          // e.g. "AFRICA"
      countryName: string,         // e.g. "Sudan"  (or countryIso2 if you prefer)
      // optional resolved refs
      regionId?: ObjectId,
      countryId?: ObjectId,

      // electrical
      voltageV?: number,
      frequencyHz?: number,

      // specification blocks
      fanSpec: {
        powerConsumptionW?: number,
        fanSpeedRpm?: number | null,
        fanSubType?: string | null
      },

      construction: {
        ductSizeMm?: number | null,
        speedControl?: "Single" | "Double" | "Variable" | null
      },

      workingPoint: {
        speed?: string, // e.g. "Hi"
        airVolume: { min: number, max: number, unit: "CMH" },
        staticPressure: { min: number, max: number, unit: "Pa" },
        noise: { value: number, unit: "dBA" } // store numeric; render “dB(A)” in UI if needed
      },

      // PQ curve data series (optional)
      pqCurves?: [
        {
          speed: string,                  // "hi"
          dashStyle?: string,             // e.g. "Solid"
          highlight?: boolean,
          highlightKey?: string,
          points: Array<{ q: number, p: number }> // q=air volume (CMH), p=pressure (Pa)
        }
      ]
    }
  ],

  // related models
  relatedModelCodes: string[],

  // assets (placeholders; may be empty)
  assets: {
    imageUrls: string[],
    documents: Array<{ label: string, url: string }>
  },

  isActive: boolean,
  createdAt: Date,
  updatedAt: Date
}
```

## Implementation notes you should require the agent to follow (to avoid common pitfalls)

* **Zod + MongoDB ObjectId**: In Zod, model ObjectId fields as `z.any()` or as `z.string().regex(/^[a-f\d]{24}$/i)` depending on whether you store IDs as strings in app code.
* **Normalize PQ curve**: Store as `{q, p}` objects rather than raw `[q,p]` tuples for readability and validation. The seed above already normalizes to objects.
* **Indexing**:
  * Unique: `modelCode`
  * Useful: `categoryCode`, `subcategoryCode`, `marketSpecs.regionCode`, `marketSpecs.countryName`
* **Future-proofing**: Keep `marketSpecs` as an array; the same model can have different electrical/spec data per country.
