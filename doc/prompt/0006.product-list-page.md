# Acceptance Criteria (Given/When/Then)

## A) Data Source Requirements (No hardcoded data)

**Given** the `/product-lists` page is rendered
**Then** all of the following must be loaded from the database (via API):

* Regions
* Countries (filtered by region)
* Categories
* Subcategories (filtered by category)
* Products (filtered by selected criteria)

**And** the UI must not contain hardcoded arrays for:

* Region list
* Country list
* Category/subcategory tree
* Product list/cards

---

## B) API Contract and Implementation Rules

### B1. Use existing API

**Given** there are existing API routes/functions used by the Home page to fetch regions/countries/categories/subcategories
**Then** reuse them as-is for `/product-lists`.

### B2. Implement missing API endpoints if needed

**If** any required endpoints do not exist
**Then** implement them following the project’s existing patterns (same folder conventions, response format, error handling, Zod validation, etc.).

### B3. Required API capabilities

Your data API must support at minimum:

1. **Get regions**

* Returns region documents from DB.

2. **Get countries by region**

* Parameter: `regionCode`
* Returns countries filtered by `regionCode`.

3. **Get categories + subcategories**

* Either:

  * return both together in one response, or
  * return categories, and a separate endpoint to return subcategories by `categoryCode`.

4. **Get products with filters**

* Must support filters used on `/product-lists`, at least:

  * `regionCode`, `countryIso2` (or equivalent key used in your countries collection)
  * `categoryCode` (optional)
  * `subcategoryCode` (optional)
  * free-text search (model code or category name) via query param, e.g. `q=...`
  * optional: voltage, air volume, static pressure if those are DB-backed in your schema

**All request input must be validated** (Zod or existing validation style used in the repo).
**All responses must be typed** (TypeScript types inferred from Zod schemas where applicable).

---

## C) Referential Integrity Enforcement

**Given** the DB contains `regions`, `countries`, `categories`, `subcategories`, and `products`
**Then** the page must enforce referential consistency at runtime:

* Country dropdown options must come from `countries` filtered by selected region.
* Subcategory options/tree must come from `subcategories` filtered by selected category.
* Product query must only use `categoryCode/subcategoryCode` values that exist in DB.
* If an invalid combination is selected (e.g., subcategory not belonging to category), reset invalid selections and show no results (or show a safe fallback state).

Additionally:

* If products reference codes that do not exist in the categories/subcategories collections, handle gracefully:

  * exclude those products from results OR
  * display them under an “Unknown” bucket (prefer exclude to preserve integrity unless explicitly required otherwise).

---

## D) Page Behavior (DB-backed)

### D1. Default empty state

**Given** Region and Country are not selected
**Then** show the empty state:

* “To see the list of products select Region & Country first”
* Button “Select Region & Country” opens filters drawer on mobile and scrolls to LOCATION on desktop

### D2. Loading states

**Given** any data call is in flight
**Then** show loading indicators:

* Skeleton cards for products
* Spinner or subtle loading UI for dropdowns

### D3. Filtering behavior

**When** Region changes
**Then**:

* reload countries from DB for that region
* reset country selection
* reset product results

**When** Country changes
**Then**:

* fetch products filtered by region/country (and other active filters)

**When** Category/Subcategory changes
**Then**:

* fetch products using the selected filters
* applied filters chips update

### D4. Search behavior (header search input)

**When** the user searches (model/category)
**Then** query products from DB using a search param (server-side filtering preferred; client-side filtering only allowed if DB returns all products for current region/country).

---

## E) Product Results Rendering

**Given** products are returned from DB
**Then** render them in grid view by default:

* image (if present; else placeholder)
* model code
* category label
* “Add To Comparison”
* report icon/button (modal UI only; generation can be stubbed)

**When** toggling list/grid
**Then** only the presentation changes; the underlying dataset remains DB-sourced.

**If** pagination exists in API
**Then** use “Show more” to fetch the next page from DB.
**If** pagination does not exist yet
**Then** implement API pagination using `limit` and `cursor`/`skip` (prefer cursor if repo already uses it).

---

## F) Implementation Guidance (non-negotiable)

1. Use `lib/db/connection.ts` as the single source of truth for:

   * Mongo client initialization
   * Collection handles
   * Collection names
2. Do not bypass the DB by embedding lists in the UI.
3. Follow existing conventions:

   * existing API folder structure
   * error format
   * response envelopes (if the repo uses them)
4. Validate query params and response mapping using Zod (or existing validation style).
5. Keep UI state minimal and derived from DB responses:

   * applied filters
   * view mode
   * comparison selection
   * modal open/close
